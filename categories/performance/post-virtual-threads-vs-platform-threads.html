Introducción: Virtual Threads vs Platform Threads

En Java, los platform threads representan el modelo tradicional de ejecución: cada hilo de aplicación se asocia directamente con un hilo del sistema operativo. Esto garantiza compatibilidad y estabilidad, pero implica un costo elevado en memoria y recursos, especialmente cuando se crean miles de hilos concurrentes.

Los virtual threads, introducidos con Project Loom, ofrecen un modelo mucho más liviano. Se ejecutan sobre un pequeño número de hilos de plataforma, pero permiten crear y gestionar millones de hilos virtuales con un consumo mínimo de recursos.

Stack más liviano:

Cada platform thread reserva un stack grande en memoria (por defecto varios MB).
Los virtual threads usan stacks mucho más pequeños y dinámicos, que se expanden según necesidad.
👉 Esto reduce el consumo de memoria por hilo.

Creación barata:

Crear un platform thread implica pedir recursos al sistema operativo.
Crear un virtual thread es una operación ligera dentro de la JVM, casi tan barata como instanciar un objeto.
👉 Podés tener millones de virtual threads sin saturar el sistema.

Multiplexación sobre carrier threads:

Los virtual threads no se ejecutan directamente en el SO, sino que se “montan” sobre un conjunto reducido de platform threads llamados carrier threads.
La JVM pausa y reanuda virtual threads sin necesidad de cambios de contexto pesados del SO.
👉 Menos overhead de scheduling.

Sección práctica: Benchmark con JMH

Para ilustrar las diferencias entre platform threads y virtual threads, se desarrolló un benchmark utilizando JMH (Java Microbenchmark Harness). Este benchmark ejecuta tareas tanto CPU-bound como I/O-bound y permite observar cómo se comportan ambos modelos bajo distintas cargas.
