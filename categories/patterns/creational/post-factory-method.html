Factory Method en Java: Construcción flexible de objetos

Cómo encapsular la creación de objetos con Factory Method para desacoplar dependencias y mejorar la extensibilidad.

← Volver a la categoría

¿Qué es el Factory Method?

El Factory Method es un patrón de diseño creacional que define una interfaz para crear objetos, pero delega a las subclases la decisión de qué clase concreta instanciar. En lugar de llamar directamente al constructor de una clase con new, se invoca un método especializado que se encarga de construir y devolver el objeto adecuado según el contexto.

Este patrón forma parte del catálogo clásico de patrones de diseño presentado por la Gang of Four (GoF) en su libro Design Patterns: Elements of Reusable Object-Oriented Software. Su propósito principal es desacoplar el código que usa un objeto del código que lo crea, favoreciendo así la extensibilidad y el mantenimiento de la aplicación a largo plazo.

Cuando hablamos de Factory Method, estamos hablando de polimorfismo aplicado a la construcción de objetos. El cliente trabaja siempre con una abstracción (interfaz o clase abstracta), sin necesidad de conocer los detalles de las implementaciones concretas que se crean detrás de escena.

El problema: acoplamiento en la creación de objetos

Imagina que estás desarrollando una aplicación que debe procesar notificaciones. Al principio, solo necesitas enviar correos electrónicos, así que escribes algo como esto directamente en tu servicio: 

public class NotificationService {

    public void send(String message) {
        EmailNotification notification = new EmailNotification();
        notification.send(message);
    }
}

El problema aparece cuando el negocio evoluciona y ahora también necesitas enviar SMS, notificaciones push y mensajes de Slack. Cada vez que surge un nuevo tipo de notificación, tienes que modificar NotificationService, añadiendo condicionales y nuevas dependencias. El código crece en complejidad y fragilidad, violando el Principio Abierto/Cerrado (Open/Closed Principle): las entidades de software deben estar abiertas para extensión, pero cerradas para modificación.

Además, la clase NotificationService queda fuertemente acoplada a las implementaciones concretas. Esto dificulta las pruebas unitarias, ya que no puedes inyectar fácilmente objetos de prueba (mocks), y complica la reutilización del código en otros contextos. El principio de inversión de dependencias nos dice que los módulos de alto nivel no deben depender de módulos de bajo nivel, sino de abstracciones; este diseño viola precisamente eso.

La solución: delegar la creación a un método especializado

La solución que propone el Factory Method consiste en introducir una abstracción para la creación del objeto. Definimos un método —el factory method— en una clase base o interfaz, y cada subclase o implementación concreta decide qué tipo de objeto construir cuando ese método es invocado.

El cliente deja de depender de las clases concretas. Solo conoce la abstracción del producto y el creador, lo que le permite trabajar de forma genérica. Cuando se necesita un nuevo tipo de producto, simplemente se crea una nueva subclase del creador que sobreescribe el factory method, sin tocar el código existente.

Aplicando este patrón a nuestro ejemplo de notificaciones, el diseño quedaría así: 

// Producto: interfaz común para todas las notificaciones
public interface Notification {
    void send(String message);
}

// Productos concretos
public class EmailNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("Enviando email: " + message);
    }
}

public class SmsNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("Enviando SMS: " + message);
    }
}

public class PushNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("Enviando notificación push: " + message);
    }
}

// Creador: define el factory method
public abstract class NotificationCreator {

    // Factory Method
    public abstract Notification createNotification();

    // Lógica de negocio que usa el producto
    public void notify(String message) {
        Notification notification = createNotification();
        notification.send(message);
    }
}

// Creadores concretos
public class EmailNotificationCreator extends NotificationCreator {
    @Override
    public Notification createNotification() {
        return new EmailNotification();
    }
}

public class SmsNotificationCreator extends NotificationCreator {
    @Override
    public Notification createNotification() {
        return new SmsNotification();
    }
}

public class PushNotificationCreator extends NotificationCreator {
    @Override
    public Notification createNotification() {
        return new PushNotification();
    }
}

Ahora, el método notify en NotificationCreator trabaja únicamente con la interfaz Notification. No importa qué implementación concreta se use; el comportamiento es correcto en todos los casos gracias al polimorfismo.

Estructura y conceptos principales

  • Producto (Product): la interfaz o clase abstracta que define el contrato que deben cumplir todos los objetos que el factory method puede crear. En nuestro ejemplo, es la interfaz Notification.
  • Producto concreto (Concrete Product): las implementaciones específicas del producto. Cada una encapsula un comportamiento particular. Son las clases EmailNotification, SmsNotification y PushNotification.
  • Creador (Creator): la clase abstracta o interfaz que declara el factory method. Puede contener lógica de negocio que depende del producto, pero delega su creación al método abstracto. Corresponde a NotificationCreator.
  • Creador concreto (Concrete Creator): sobreescribe el factory method para devolver una instancia de un producto concreto específico. Son las clases EmailNotificationCreator, SmsNotificationCreator y PushNotificationCreator.
  • Polimorfismo: el mecanismo clave que permite que el creador trabaje con cualquier producto concreto a través de la interfaz común, sin necesidad de conocer su tipo exacto en tiempo de compilación.
  • Inversión de dependencias: tanto el creador como el cliente dependen de abstracciones (Notification), no de implementaciones concretas, siguiendo el principio DIP de SOLID.

Ejemplo en Java: Factory Method con parámetro de selección

Una variante muy habitual del patrón en proyectos reales es implementar el factory method con un parámetro que determina qué tipo de objeto se debe crear. Esto centraliza la lógica de selección en un único punto y simplifica el código del cliente: 

public enum NotificationType {
    EMAIL, SMS, PUSH
}

public class NotificationFactory {

    public static Notification create(NotificationType type) {
        return switch (type) {
            case EMAIL -> new EmailNotification();
            case SMS   -> new SmsNotification();
            case PUSH  -> new PushNotification();
        };
    }
}

// Uso desde el cliente
public class Application {

    public static void main(String[] args) {
        Notification notification = NotificationFactory.create(NotificationType.EMAIL);
        notification.send("Tu pedido ha sido confirmado.");

        Notification sms = NotificationFactory.create(NotificationType.SMS);
        sms.send("Tu código de verificación es 4821.");
    }
}

Esta variante, conocida a veces como Static Factory Method, no sigue al pie de la letra la estructura original del GoF —ya que no usa herencia para delegar la creación—, pero es ampliamente utilizada por su simplicidad y es perfectamente válida cuando no se necesita extender el creador mediante subclases. Java mismo la emplea en métodos como List.of(), Optional.of() o LocalDate.of().

¿Cuándo usarlo?

  • Cuando el código que crea objetos no debe conocer de antemano el tipo exacto de objeto que necesita, sino trabajar con una abstracción.
  • Cuando anticipas que el sistema deberá soportar nuevos tipos de productos en el futuro y quieres que esas extensiones no requieran modificar el código existente.
  • Cuando la lógica de creación de un objeto es compleja o reutilizable y conviene encapsularla en un único lugar para evitar duplicación.
  • Cuando deseas facilitar las pruebas unitarias, permitiendo que el creador sea sustituido por una implementación de prueba que devuelva objetos mock o stub.
  • Cuando trabajas con frameworks o librerías que esperan que registres o configures creadores de objetos (por ejemplo, BeanFactory en Spring).

Ventajas y desventajas

Ventajas

  • Desacoplamiento: el cliente trabaja con abstracciones, lo que reduce las dependencias entre módulos y hace el código más flexible y mantenible.
  • Extensibilidad: añadir un nuevo tipo de producto solo requiere crear una nueva subclase del creador, sin modificar el código existente. Se respeta el Principio Abierto/Cerrado.
  • Testabilidad: al depender de interfaces, es sencillo inyectar implementaciones de prueba y escribir tests unitarios limpios y aislados.
  • Responsabilidad única: la lógica de creación queda centralizada en el creador, separándola de la lógica de negocio del cliente.

Desventajas

  • Mayor complejidad inicial: introduce más clases e interfaces en el diseño, lo que puede resultar excesivo para casos simples donde una única implementación es suficiente.
  • Jerarquía paralela: por cada nuevo producto concreto suele ser necesario crear también un nuevo creador concreto, lo que puede llevar a una proliferación de clases difícil de gestionar en proyectos muy grandes.
  • Curva de aprendizaje: para desarrolladores menos familiarizados con patrones de diseño, el nivel de abstracción puede dificultar la comprensión inicial del flujo del programa.
