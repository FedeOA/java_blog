Factory Method en Java: Construcción flexible de objetos

Cómo encapsular la creación de objetos con Factory Method para desacoplar dependencias y mejorar la extensibilidad.

← Volver a la categoría

¿Qué es el Factory Method?

El Factory Method es un patrón de diseño creacional que proporciona una interfaz para crear objetos sin especificar exactamente qué clases concretas se instanciarán. En lugar de utilizar el operador new directamente en el código cliente, delegamos la creación de objetos a métodos especializados que actúan como "fábricas". Este enfoque encapsula la lógica de instanciación y permite que las subclases decidan qué tipo de objeto crear, promoviendo así un código más flexible, mantenible y desacoplado.

El Factory Method es especialmente útil cuando una clase no puede anticipar el tipo de objetos que necesita crear, o cuando deseas permitir que las subclases especifiquen los objetos que crearán. Este patrón es fundamental en arquitecturas orientadas a objetos modernas y se encuentra en innumerables frameworks y librerías Java populares.

Problema que resuelve

Sin el Factory Method, el código cliente debe conocer todas las clases concretas que podría necesitar instanciar. Esto genera varios problemas significativos:

Acoplamiento fuerte: El código cliente está directamente acoplado a las implementaciones concretas. Si necesitas agregar una nueva clase o cambiar la lógica de instanciación, debes modificar el código cliente en múltiples lugares.

Dificultad para mantener: Cuando la lógica de creación es compleja (requiere validaciones, configuraciones especiales o decisiones basadas en parámetros), esta lógica se dispersa por toda la aplicación, haciendo el código difícil de mantener.

Falta de extensibilidad: Agregar nuevos tipos de objetos requiere cambios en el código existente, violando el principio Open/Closed (abierto para extensión, cerrado para modificación).

Pruebas unitarias complicadas: Es difícil mockear o reemplazar las dependencias cuando están fuertemente acopladas a través de instanciación directa.

Consideremos un ejemplo: una aplicación que trabaja con diferentes tipos de conexiones a bases de datos (MySQL, PostgreSQL, MongoDB). Sin Factory Method, cada parte del código que necesita una conexión debe saber cómo instanciar la clase correcta, resultando en código repetitivo y frágil.

Solución

El Factory Method resuelve estos problemas al centralizar la creación de objetos en métodos especializados. La solución se basa en dos principios clave:

Abstracción de la creación: En lugar de instanciar directamente, el código cliente llama a un método factory que retorna un objeto del tipo esperado. El cliente no necesita conocer la clase concreta específica.

Polimorfismo: Las subclases pueden sobrescribir el método factory para retornar diferentes tipos de objetos, permitiendo que la decisión sobre qué crear se tome en tiempo de ejecución.

Esta aproximación desacopla el código cliente de las implementaciones concretas, permitiendo que nuevas clases se agreguen sin modificar el código existente. La lógica de creación se centraliza en un lugar, facilitando el mantenimiento y las pruebas.

Estructura y conceptos principales

  • Product (Producto): La interfaz o clase abstracta que define el contrato para los objetos que la fábrica creará. Todos los productos concretos implementan esta interfaz.
  • ConcreteProduct (Producto Concreto): Las implementaciones específicas del producto. Cada una representa un tipo diferente de objeto que la fábrica puede crear.
  • Creator (Creador): La clase abstracta o interfaz que declara el método factory. Contiene la lógica que depende del producto abstracto, no de las clases concretas.
  • ConcreteCreator (Creador Concreto): Las subclases que implementan el método factory para crear productos concretos específicos. Cada creador concreto sabe cómo instanciar su correspondiente producto concreto.
  • Inversión de dependencias: El código cliente depende de abstracciones (interfaces/clases abstractas), no de implementaciones concretas, siguiendo el principio de inversión de dependencias.

Ejemplo en Java: Sistema de Transporte

Veamos un ejemplo práctico donde una empresa de logística necesita trabajar con diferentes tipos de transporte (camiones, barcos, aviones). Cada tipo tiene su propia implementación, pero el código cliente debe trabajar con cualquiera de ellos de manera uniforme.


// Interfaz del Producto
public interface Transporte {
    void entregar(String destino);
    double calcularCosto(double distancia);
}

// Productos Concretos
public class Camion implements Transporte {
    @Override
    public void entregar(String destino) {
        System.out.println("Entregando por carretera a: " + destino);
    }
    
    @Override
    public double calcularCosto(double distancia) {
        return distancia * 0.5; // $0.50 por km
    }
}

public class Barco implements Transporte {
    @Override
    public void entregar(String destino) {
        System.out.println("Entregando por mar a: " + destino);
    }
    
    @Override
    public double calcularCosto(double distancia) {
        return distancia * 0.2; // $0.20 por km
    }
}

public class Avion implements Transporte {
    @Override
    public void entregar(String destino) {
        System.out.println("Entregando por aire a: " + destino);
    }
    
    @Override
    public double calcularCosto(double distancia) {
        return distancia * 1.5; // $1.50 por km
    }
}

// Clase Creadora Abstracta
public abstract class Logistica {
    public abstract Transporte crearTransporte();
    
    public void planificarEntrega(String destino, double distancia) {
        Transporte transporte = crearTransporte();
        transporte.entregar(destino);
        double costo = transporte.calcularCosto(distancia);
        System.out.println("Costo de entrega: $" + costo);
    }
}

// Creadores Concretos
public class LogisticaTerrestre extends Logistica {
    @Override
    public Transporte crearTransporte() {
        return new Camion();
    }
}

public class LogisticaMaritima extends Logistica {
    @Override
    public Transporte crearTransporte() {
        return new Barco();
    }
}

public class LogisticaAerea extends Logistica {
    @Override
    public Transporte crearTransporte() {
        return new Avion();
    }
}

// Uso del patrón
public class Main {
    public static void main(String[] args) {
        Logistica logistica = new LogisticaTerrestre();
        logistica.planificarEntrega("Madrid", 500);
        
        logistica = new LogisticaMaritima();
        logistica.planificarEntrega("Barcelona", 1000);
        
        logistica = new LogisticaAerea();
        logistica.planificarEntrega("Sevilla", 300);
    }
}

Ejemplo avanzado: Factory Method con parámetros

En muchos casos, necesitamos que el factory method tome decisiones basadas en parámetros. Aquí mostramos un ejemplo de un sistema de notificaciones que crea diferentes tipos de notificadores según el tipo especificado:


// Interfaz del Producto
public interface Notificador {
    void enviar(String mensaje, String destinatario);
}

// Productos Concretos
public class NotificadorEmail implements Notificador {
    @Override
    public void enviar(String mensaje, String destinatario) {
        System.out.println("Email enviado a " + destinatario + ": " + mensaje);
    }
}

public class NotificadorSMS implements Notificador {
    @Override
    public void enviar(String mensaje, String destinatario) {
        System.out.println("SMS enviado a " + destinatario + ": " + mensaje);
    }
}

public class NotificadorPushNotification implements Notificador {
    @Override
    public void enviar(String mensaje, String destinatario) {
        System.out.println("Push notification enviada a " + destinatario + ": " + mensaje);
    }
}

// Factory Method con parámetros
public class FabricaNotificadores {
    public static Notificador crearNotificador(String tipo) {
        switch(tipo.toLowerCase()) {
            case "email":
                return new NotificadorEmail();
            case "sms":
                return new NotificadorSMS();
            case "push":
                return new NotificadorPushNotification();
            default:
                throw new IllegalArgumentException("Tipo de notificador no soportado: " + tipo);
        }
    }
}

// Uso
public class SistemaNotificaciones {
    public static void main(String[] args) {
        Notificador notificador = FabricaNotificadores.crearNotificador("email");
        notificador.enviar("Bienvenido", "usuario@example.com");
        
        notificador = FabricaNotificadores.crearNotificador("sms");
        notificador.enviar("Tu código es 1234", "+34612345678");
    }
}

Ejemplo con Enums y Factory Method

Una forma moderna y type-safe de implementar Factory Method es utilizando enums. Esto proporciona una solución elegante y segura:


public interface BaseDatos {
    void conectar();
    void ejecutarQuery(String sql);
}

public class MySQL implements BaseDatos {
    @Override
    public void conectar() {
        System.out.println("Conectando a MySQL...");
    }
    
    @Override
    public void ejecutarQuery(String sql) {
        System.out.println("Ejecutando en MySQL: " + sql);
    }
}

public class PostgreSQL implements BaseDatos {
    @Override
    public void conectar() {
        System.out.println("Conectando a PostgreSQL...");
    }
    
    @Override
    public void ejecutarQuery(String sql) {
        System.out.println("Ejecutando en PostgreSQL: " + sql);
    }
}

public enum TipoBaseDatos {
    MYSQL(MySQL::new),
    POSTGRESQL(PostgreSQL::new);
    
    private final java.util.function.Supplier constructor;
    
    TipoBaseDatos(java.util.function.Supplier constructor) {
        this.constructor = constructor;
    }
    
    public BaseDatos crear() {
        return constructor.get();
    }
}

// Uso
public class ConexionBD {
    public static void main(String[] args) {
        BaseDatos bd = TipoBaseDatos.MYSQL.crear();
        bd.conectar();
        bd.ejecutarQuery("SELECT * FROM usuarios");
        
        bd = TipoBaseDatos.POSTGRESQL.crear();
        bd.conectar();
        bd.ejecutarQuery("SELECT * FROM usuarios");
    }
}

¿Cuándo usarlo?

  • Múltiples implementaciones: Cuando una clase puede tener varias implementaciones y necesitas elegir cuál usar en tiempo de ejecución.
  • Desconocimiento de tipos concretos: Cuando el código cliente no debe conocer las clases concretas específicas que necesita crear.
  • Lógica de creación compleja: Cuando la instanciación requiere validaciones, configuraciones especiales o decisiones complejas.
  • Extensibilidad futura: Cuando anticipas que nuevos tipos de productos se agregarán en el futuro sin modificar el código existente.
  • Inyección de dependencias: Cuando trabajas con frameworks que requieren control sobre la creación de objetos.
  • Pruebas unitarias: Cuando necesitas mockear o reemplazar fácilmente las dependencias en tus tests.
  • Frameworks y librerías: Cuando desarrollas frameworks que deben permitir a los usuarios extender funcionalidad creando nuevas implementaciones.

Ventajas y desventajas

Ventajas

  • Desacoplamiento: El código cliente está desacoplado de las clases concretas, dependiendo solo de abstracciones.
  • Flexibilidad: Puedes cambiar o agregar nuevas implementaciones sin modificar el código cliente.
  • Centralización: La lógica de creación se centraliza en un lugar, facilitando el mantenimiento y los cambios.
  • Principio Open/Closed: El código está abierto para extensión (nuevas clases) pero cerrado para modificación.
  • Testabilidad: Facilita las pruebas unitarias al permitir inyectar implementaciones mock o stub.
  • Responsabilidad única: Cada clase tiene una responsabilidad clara: crear o usar objetos, no ambas.
  • Polimorfismo en tiempo de ejecución: Permite tomar decisiones sobre qué tipo de objeto crear en tiempo de ejecución.

Desventajas

  • Complejidad adicional: Introduce clases y abstracciones adicionales que pueden ser excesivas para casos simples.
  • Curva de aprendizaje: Desarrolladores menos experimentados pueden encontrar el patrón confuso inicialmente.
