Singleton en Java: Controlando la instancia única

Cómo implementar el patrón Singleton para garantizar una sola instancia y controlar el acceso global a recursos compartidos.

← Volver a la categoría

¿Qué es el patrón Singleton?

El patrón Singleton es uno de los patrones de diseño creacionales más conocidos y utilizados en el desarrollo de software. Su objetivo principal es garantizar que una clase tenga una única instancia durante todo el ciclo de vida de la aplicación, proporcionando además un punto de acceso global a esa instancia.

Este patrón fue formalizado por la Gang of Four (GoF) en su libro clásico Design Patterns: Elements of Reusable Object-Oriented Software y sigue siendo una herramienta fundamental en el arsenal de cualquier desarrollador Java. La idea central es simple: en lugar de crear objetos libremente con new, la propia clase se encarga de controlar su instanciación y de ofrecer siempre el mismo objeto a quien lo solicite.

Problema que resuelve

Imagina que estás desarrollando una aplicación que necesita gestionar la conexión a una base de datos, un sistema de logging o un registro de configuración global. Si cada componente de tu aplicación creara su propia instancia de estas clases, enfrentarías varios problemas graves:

  • Desperdicio de recursos: Abrir múltiples conexiones a una base de datos consume memoria y tiempo innecesariamente.
  • Inconsistencia de estado: Si dos partes de la aplicación modifican objetos distintos creyendo que comparten el mismo estado, los datos pueden volverse inconsistentes.
  • Dificultad de coordinación: Sin un punto de acceso único, coordinar el acceso concurrente a recursos compartidos se vuelve extremadamente complejo.

El patrón Singleton resuelve todos estos problemas al centralizar la creación y el acceso a un objeto, asegurando que solo exista uno en toda la aplicación.

Solución: implementando Singleton en Java

La implementación básica del patrón Singleton en Java requiere tres elementos fundamentales:

  • Un constructor privado que impide la instanciación directa desde fuera de la clase.
  • Un atributo estático privado que almacena la única instancia de la clase.
  • Un método estático público, generalmente llamado getInstance(), que devuelve la instancia existente o la crea si aún no existe.

La implementación más simple, conocida como Lazy Initialization, crea la instancia solo cuando se necesita por primera vez:

public class ConfigurationManager {

    // Instancia única de la clase
    private static ConfigurationManager instance;

    // Propiedades de configuración
    private String databaseUrl;
    private int maxConnections;

    // Constructor privado para evitar instanciación externa
    private ConfigurationManager() {
        this.databaseUrl = "jdbc:mysql://localhost:3306/mydb";
        this.maxConnections = 10;
    }

    // Método de acceso global a la instancia
    public static ConfigurationManager getInstance() {
        if (instance == null) {
            instance = new ConfigurationManager();
        }
        return instance;
    }

    public String getDatabaseUrl() {
        return databaseUrl;
    }

    public int getMaxConnections() {
        return maxConnections;
    }
}

Sin embargo, esta implementación tiene un problema importante: no es thread-safe. En un entorno multihilo, dos hilos podrían ejecutar simultáneamente la comprobación if (instance == null) y crear dos instancias distintas, rompiendo la garantía del patrón.

Singleton thread-safe: variantes avanzadas

En aplicaciones Java reales, el acceso concurrente es la norma, no la excepción. Por ello, es fundamental conocer las distintas estrategias para implementar un Singleton seguro en entornos multihilo.

Double-Checked Locking

Esta técnica utiliza synchronized solo en el momento crítico de la creación, evitando el coste de sincronización en cada llamada a getInstance(). La palabra clave volatile es esencial para garantizar la visibilidad correcta entre hilos: 

public class DatabaseConnection {

    // volatile garantiza visibilidad entre hilos
    private static volatile DatabaseConnection instance;

    private String connectionUrl;

    private DatabaseConnection() {
        this.connectionUrl = "jdbc:postgresql://localhost:5432/app";
        System.out.println("Conexión a base de datos inicializada.");
    }

    public static DatabaseConnection getInstance() {
        if (instance == null) {                        // Primera comprobación (sin lock)
            synchronized (DatabaseConnection.class) {
                if (instance == null) {                // Segunda comprobación (con lock)
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }

    public String getConnectionUrl() {
        return connectionUrl;
    }

    public void executeQuery(String query) {
        System.out.println("Ejecutando en [" + connectionUrl + "]: " + query);
    }
}

Initialization-on-demand Holder (la mejor opción)

Esta variante aprovecha la garantía de la JVM de que la inicialización de clases es thread-safe por definición. Es la implementación recomendada en la mayoría de los casos porque es lazy, thread-safe y no requiere sincronización explícita: 

public class Logger {

    // Constructor privado
    private Logger() {
        System.out.println("Logger inicializado.");
    }

    // Clase interna estática que contiene la instancia
    private static class LoggerHolder {
        private static final Logger INSTANCE = new Logger();
    }

    // Acceso a la instancia única
    public static Logger getInstance() {
        return LoggerHolder.INSTANCE;
    }

    public void log(String nivel, String mensaje) {
        System.out.printf("[%s] %s: %s%n",
            java.time.LocalDateTime.now(), nivel, mensaje);
    }

    public void info(String mensaje) {
        log("INFO", mensaje);
    }

    public void error(String mensaje) {
        log("ERROR", mensaje);
    }
}

// Uso en la aplicación
class Application {
    public static void main(String[] args) {
        Logger logger = Logger.getInstance();
        logger.info("Aplicación iniciada.");

        // Verificamos que siempre es la misma instancia
        Logger otroLogger = Logger.getInstance();
        System.out.println("¿Misma instancia? " + (logger == otroLogger)); // true

        otroLogger.error("Esto es un error de prueba.");
    }
}

En este ejemplo, la clase interna LoggerHolder solo se carga cuando se accede por primera vez a getInstance(), garantizando tanto la inicialización perezosa como la seguridad en entornos concurrentes sin coste adicional.

Estructura y conceptos principales

  • Constructor privado: Impide que otras clases creen instancias usando new, delegando el control completamente a la propia clase.
  • Atributo estático: Almacena la referencia a la única instancia en el nivel de clase, no de objeto, para que persista durante toda la ejecución.
  • Método getInstance(): Punto de acceso global que garantiza la devolución de la misma instancia en cada invocación.
  • Lazy Initialization: Estrategia de creación diferida donde la instancia solo se construye cuando se necesita por primera vez, ahorrando recursos si nunca se usa.
  • Eager Initialization: La instancia se crea al cargar la clase, independientemente de si se va a usar. Más simple pero consume recursos desde el inicio.
  • volatile: Modificador que asegura que los cambios en la variable sean visibles inmediatamente para todos los hilos, crucial en la implementación Double-Checked Locking.
  • Holder Pattern: Técnica que delega la inicialización a una clase interna estática, aprovechando las garantías de thread-safety de la JVM sin sincronización manual.

¿Cuándo usarlo?

  • Cuando necesitas un gestor de configuración que cargue propiedades del sistema una sola vez y las comparta en toda la aplicación.
  • Para implementar un sistema de logging centralizado que todos los módulos de la aplicación puedan utilizar sin crear instancias propias.
  • En la gestión de pools de conexiones a bases de datos o servicios externos, donde crear múltiples pools sería costoso e innecesario.
  • Cuando implementas un registro de servicios (Service Registry) o un contenedor de dependencias simple.
  • Para gestionar el acceso a recursos hardware que solo pueden ser controlados por un único punto, como impresoras, puertos seriales o dispositivos de lectura.
  • En la implementación de cachés en memoria compartidas entre distintos componentes de la aplicación.

Ventajas y desventajas

Ventajas

  • Control absoluto sobre la instanciación: Garantiza que solo exista un objeto en toda la aplicación, eliminando inconsistencias de estado.
  • Ahorro de recursos: Evita la creación repetida de objetos costosos, como conexiones a bases de datos o lectores de configuración.
  • Acceso global sencillo: Cualquier parte de la aplicación puede acceder al objeto compartido sin necesidad de pasarlo como parámetro.
  • Inicialización controlada: Con Lazy Initialization, el objeto solo se crea si realmente se necesita, optimizando el arranque de la aplicación.

Desventajas

  • Dificultad para testear: El estado global que introduce el Singleton complica las pruebas unitarias, ya que el estado de una prueba puede afectar a las demás si no se resetea correctamente.
  • Acoplamiento elevado: Las clases que dependen directamente de un Singleton están fuertemente acopladas a él, reduciendo la flexibilidad y dificultando la sustitución por implementaciones alternativas.
  • Violación del Principio de Responsabilidad Única: La clase asume la responsabilidad de gestionar su propia creación además de su lógica de negocio.
  • Problemas en entornos distribuidos: En arquitecturas de microservicios o aplicaciones con múltiples JVMs, cada instancia tiene su propio Singleton, por lo que el patrón no garantiza unicidad a nivel de sistema distribuido.
  • Considerado un antipatrón en algunos contextos: Un uso excesivo o inadecuado puede llevar a un diseño rígido y difícil de mantener. Se recomienda evaluar si la inyección de dependencias (DI) no es una solución más apropiada.
