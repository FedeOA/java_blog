Composite en Java: Tratando objetos y grupos de forma uniforme

Cómo modelar jerarquías de objetos usando Composite para tratar nodos y hojas con la misma API.

← Volver a la categoría

¿Qué es el patrón Composite?

El patrón Composite es un patrón de diseño estructural que permite componer objetos en estructuras de árbol para representar jerarquías parte-todo. Su característica más poderosa es que permite tratar tanto los objetos individuales (hojas) como las composiciones de objetos (nodos) de manera uniforme, usando la misma interfaz para ambos.

Imagina que estás modelando el sistema de archivos de un ordenador: tienes carpetas que pueden contener otras carpetas o archivos individuales. Desde el punto de vista del sistema, tanto una carpeta como un archivo deben poder ser tratados de la misma forma para operaciones como calcular el tamaño o listar el contenido. Esto es exactamente lo que Composite hace posible.

Este patrón pertenece a la categoría de patrones estructurales, definidos por la Gang of Four en su libro clásico Design Patterns, y su aplicación es especialmente valiosa cuando la lógica de negocio necesita operar sobre árboles de objetos sin distinguir si está tratando con un elemento simple o con un contenedor complejo.

Problema que resuelve

Cuando trabajamos con estructuras jerárquicas en Java, el enfoque más directo sería tratar los contenedores y los elementos individuales con clases completamente diferentes, usando comprobaciones de tipo (instanceof) para decidir qué operación aplicar en cada caso. Este enfoque genera código frágil, difícil de mantener y muy acoplado.

Por ejemplo, si tenemos un sistema de menús en una aplicación donde un menú puede contener ítems simples u otros submenús, el código cliente tendría que saber en todo momento con qué tipo de objeto está tratando. Cada vez que se agrega un nuevo tipo de componente, el código cliente debe modificarse. Esto viola el principio abierto/cerrado y el principio de responsabilidad única.

El resultado es una explosión de condicionales, duplicación de lógica y una arquitectura que se resiste al cambio. Composite elimina este problema al definir una interfaz común que tanto hojas como compuestos implementan, de modo que el cliente nunca necesita saber con cuál está interactuando.

Estructura y conceptos principales

El patrón Composite se articula en torno a tres participantes fundamentales:

  • Component (Componente): es la interfaz o clase abstracta que define las operaciones comunes para todos los objetos de la jerarquía, tanto simples como compuestos. Es el contrato que unifica el tratamiento de hojas y nodos.
  • Leaf (Hoja): representa los objetos básicos de la jerarquía, aquellos que no tienen hijos. Implementa el comportamiento base de la interfaz Component. Las hojas son los bloques de construcción fundamentales del árbol.
  • Composite (Compuesto): es el nodo que puede contener otros componentes, tanto hojas como otros compuestos. Implementa la interfaz Component delegando las operaciones a sus hijos y puede agregar lógica adicional antes o después de dicha delegación.
  • Client (Cliente): interactúa con todos los elementos a través de la interfaz Component, sin necesidad de conocer si está tratando con una hoja o un compuesto.

La clave del patrón es que el Composite mantiene una colección de referencias a sus hijos de tipo Component, lo que le permite construir árboles de profundidad arbitraria de forma recursiva.

Ejemplo en Java: Sistema de archivos

Veamos cómo modelar un sistema de archivos simple usando Composite. Primero definimos la interfaz común y luego las implementaciones para archivos y directorios. 


// Component: interfaz común para archivos y directorios
public interface FileSystemComponent {
    String getName();
    int getSize();
    void print(String indent);
}

// Leaf: representa un archivo individual
public class File implements FileSystemComponent {

    private final String name;
    private final int size;

    public File(String name, int size) {
        this.name = name;
        this.size = size;
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public int getSize() {
        return size;
    }

    @Override
    public void print(String indent) {
        System.out.println(indent + "📄 " + name + " (" + size + " KB)");
    }
}

// Composite: representa un directorio que puede contener archivos u otros directorios
public class Directory implements FileSystemComponent {

    private final String name;
    private final List children = new ArrayList<>();

    public Directory(String name) {
        this.name = name;
    }

    public void add(FileSystemComponent component) {
        children.add(component);
    }

    public void remove(FileSystemComponent component) {
        children.remove(component);
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public int getSize() {
        return children.stream()
                .mapToInt(FileSystemComponent::getSize)
                .sum();
    }

    @Override
    public void print(String indent) {
        System.out.println(indent + "📁 " + name + " (" + getSize() + " KB)");
        for (FileSystemComponent child : children) {
            child.print(indent + "    ");
        }
    }
}

Observa que el método getSize() en Directory delega recursivamente en sus hijos. No importa si un hijo es un File o un Directory anidado: ambos responden al mismo mensaje gracias a la interfaz común.

Usando el Composite: el cliente en acción

Veamos ahora cómo el código cliente construye y opera sobre el árbol de componentes de forma completamente uniforme, sin ningún instanceof ni lógica condicional basada en tipos: 


public class CompositeDemo {

    public static void main(String[] args) {

        // Creamos archivos individuales (hojas)
        File readme = new File("README.md", 5);
        File main = new File("Main.java", 20);
        File utils = new File("Utils.java", 15);
        File config = new File("config.yml", 3);
        File logo = new File("logo.png", 150);

        // Creamos directorios (compuestos)
        Directory src = new Directory("src");
        src.add(main);
        src.add(utils);

        Directory resources = new Directory("resources");
        resources.add(config);
        resources.add(logo);

        Directory project = new Directory("my-project");
        project.add(readme);
        project.add(src);
        project.add(resources);

        // El cliente trata todo con la misma interfaz
        System.out.println("=== Estructura del proyecto ===");
        project.print("");

        System.out.println("\nTamaño total del proyecto: " + project.getSize() + " KB");
        System.out.println("Tamaño de /src: " + src.getSize() + " KB");
        System.out.println("Tamaño de README.md: " + readme.getSize() + " KB");
    }
}

/*
Salida esperada:
=== Estructura del proyecto ===
📁 my-project (193 KB)
    📄 README.md (5 KB)
    📁 src (35 KB)
        📄 Main.java (20 KB)
        📄 Utils.java (15 KB)
    📁 resources (153 KB)
        📄 config.yml (3 KB)
        📄 logo.png (150 KB)

Tamaño total del proyecto: 193 KB
Tamaño de /src: 35 KB
Tamaño de README.md: 5 KB
*/

El cliente llama a getSize() y print() indiferentemente sobre project, src o readme. La recursividad del patrón se encarga del resto de forma transparente.

¿Cuándo usarlo?

  • Cuando necesitas representar jerarquías parte-todo de objetos, como árboles de componentes de UI, estructuras de menús, organigramas o sistemas de archivos.
  • Cuando quieres que el código cliente pueda ignorar la diferencia entre objetos simples y compuestos, interactuando con ambos a través de una interfaz uniforme.
  • Cuando la estructura del árbol puede variar en profundidad y anchura de forma dinámica en tiempo de ejecución y necesitas que el sistema lo soporte sin cambios en el cliente.
  • En el contexto de frameworks de renderizado de interfaces gráficas, donde paneles contienen widgets que a su vez pueden contener otros paneles.
  • Al modelar expresiones matemáticas o lógicas donde los operadores contienen operandos que pueden ser valores simples u otras expresiones.
  • En sistemas de permisos o roles jerárquicos, donde un grupo de permisos puede contener permisos individuales u otros grupos.

Ventajas y desventajas

Ventajas

  • Uniformidad en el tratamiento: el cliente trabaja con hojas y compuestos usando la misma interfaz, simplificando enormemente el código y eliminando condicionales basados en tipos.
  • Extensibilidad sencilla: agregar nuevos tipos de componentes (nuevas hojas o nuevos tipos de compuestos) no requiere modificar el código cliente ni las clases existentes, respetando el principio abierto/cerrado.
  • Recursividad natural: las operaciones sobre estructuras de árbol se implementan de forma limpia y elegante mediante la delegación recursiva, sin necesitar algoritmos externos complejos.
  • Modularidad: es fácil construir estructuras complejas combinando componentes simples, favoreciendo la reutilización y la composición sobre la herencia.

Desventajas

  • Interfaz demasiado general: al unificar la interfaz para hojas y compuestos, a veces se incluyen operaciones (como add() o remove()) que no tienen sentido en las hojas, lo que puede llevar a implementaciones vacías o excepciones en tiempo de ejecución.
  • Dificultad para restringir tipos de hijos: el sistema de tipos de Java no siempre permite imponer restricciones sobre qué tipos de componentes puede contener un compuesto concreto, requiriendo validaciones en tiempo de ejecución.
  • Complejidad oculta: el comportamiento recursivo puede dificultar el depurado cuando los árboles son muy profundos o cuando una operación produce efectos inesperados por la delegación en cascada.
  • Rendimiento en árboles grandes: operaciones como getSize() que recorren todo el árbol en cada llamada pueden ser costosas si la jerarquía es muy extensa y no se implementa algún mecanismo de caché.
