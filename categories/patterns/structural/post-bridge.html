Bridge en Java: Separando abstracción de implementación

Cómo separar la interfaz del comportamiento de la implementación para reducir el acoplamiento y facilitar extensiones.

← Volver a la categoría

¿Qué es el patrón Bridge?

El patrón Bridge es un patrón de diseño estructural que tiene como objetivo separar una abstracción de su implementación, de modo que ambas puedan evolucionar de forma independiente. En lugar de crear una jerarquía de clases que combine ambas dimensiones, Bridge las divide en dos jerarquías distintas conectadas mediante una referencia (el "puente").

Este patrón pertenece al catálogo original de los Gang of Four y resulta especialmente útil cuando una clase puede variar en múltiples dimensiones ortogonales. En lugar de multiplicar subclases para cubrir cada combinación posible, Bridge permite extender cada dimensión de forma independiente, reduciendo drásticamente la complejidad del sistema.

Dicho de forma sencilla: si tienes una abstracción que necesita diferentes implementaciones, y además esa abstracción puede tener variantes, Bridge es la herramienta adecuada para mantener el código limpio y extensible.

El problema: explosión de subclases

Imagina que estás desarrollando una aplicación que gestiona notificaciones. Tienes dos tipos de notificaciones (EmailNotification y SMSNotification) y dos niveles de urgencia (Normal y Urgente). Si usas herencia clásica, necesitarías cuatro clases:

  • NormalEmailNotification
  • UrgentEmailNotification
  • NormalSMSNotification
  • UrgentSMSNotification

Ahora añade un tercer canal, como PushNotification, y un tercer nivel de urgencia. El número de subclases crece de forma exponencial. Este fenómeno se conoce como explosión de subclases y hace que el código sea difícil de mantener, difícil de probar y muy frágil ante cambios.

El problema de fondo es que se están mezclando dos conceptos que deberían permanecer separados: qué hace la notificación (la abstracción) y cómo lo hace (la implementación). La herencia crea un acoplamiento rígido entre ambos, lo que impide que evolucionen de manera independiente.

La solución: conectar dos jerarquías independientes

Bridge resuelve este problema dividiendo el diseño en dos jerarquías separadas:

  • Abstracción: define la interfaz de alto nivel que el cliente utiliza. Contiene una referencia a la implementación.
  • Implementación: define la interfaz de bajo nivel que realiza el trabajo concreto.

La abstracción delega el trabajo real en el objeto de implementación. Gracias a esta separación, puedes añadir nuevas abstracciones o nuevas implementaciones sin modificar el código existente, respetando el principio Open/Closed.

Veamos cómo se traduce esto en código Java. Primero definimos la interfaz de implementación y sus implementaciones concretas: 


// Interfaz de implementación
public interface MessageSender {
    void sendMessage(String recipient, String message);
}

// Implementación concreta: Email
public class EmailSender implements MessageSender {
    @Override
    public void sendMessage(String recipient, String message) {
        System.out.println("[EMAIL] Para: " + recipient + " | Mensaje: " + message);
    }
}

// Implementación concreta: SMS
public class SMSSender implements MessageSender {
    @Override
    public void sendMessage(String recipient, String message) {
        System.out.println("[SMS] Para: " + recipient + " | Mensaje: " + message);
    }
}

// Implementación concreta: Push Notification
public class PushSender implements MessageSender {
    @Override
    public void sendMessage(String recipient, String message) {
        System.out.println("[PUSH] Para: " + recipient + " | Mensaje: " + message);
    }
}

Ahora definimos la jerarquía de abstracción. La clase base Notification mantiene una referencia al MessageSender y delega en él el envío real: 


// Abstracción base
public abstract class Notification {
    protected MessageSender sender;

    public Notification(MessageSender sender) {
        this.sender = sender;
    }

    public abstract void notify(String recipient, String message);
}

// Abstracción refinada: notificación normal
public class NormalNotification extends Notification {

    public NormalNotification(MessageSender sender) {
        super(sender);
    }

    @Override
    public void notify(String recipient, String message) {
        sender.sendMessage(recipient, message);
    }
}

// Abstracción refinada: notificación urgente
public class UrgentNotification extends Notification {

    public UrgentNotification(MessageSender sender) {
        super(sender);
    }

    @Override
    public void notify(String recipient, String message) {
        String urgentMessage = "🚨 URGENTE: " + message;
        sender.sendMessage(recipient, urgentMessage);
    }
}

Estructura y conceptos principales

  • Abstraction (Abstracción): clase base de la jerarquía de alto nivel. Define la interfaz que usa el cliente y mantiene una referencia al objeto Implementor. En el ejemplo, es Notification.
  • RefinedAbstraction (Abstracción Refinada): extiende la abstracción base añadiendo o modificando comportamiento. En el ejemplo, son NormalNotification y UrgentNotification.
  • Implementor (Implementador): interfaz de bajo nivel que define las operaciones concretas. En el ejemplo, es MessageSender.
  • ConcreteImplementor (Implementador Concreto): implementa la interfaz Implementor con lógica específica. En el ejemplo, son EmailSender, SMSSender y PushSender.
  • Composición sobre herencia: la abstracción no hereda de la implementación, sino que la contiene. Esta es la clave del patrón y lo que lo diferencia de una simple herencia múltiple.

Ejemplo en Java: uso desde el cliente

Una vez definidas ambas jerarquías, el cliente puede combinarlas libremente en tiempo de ejecución sin necesidad de modificar ninguna clase existente: 


public class Main {
    public static void main(String[] args) {

        // Notificación normal por Email
        Notification normalEmail = new NormalNotification(new EmailSender());
        normalEmail.notify("usuario@ejemplo.com", "Tu pedido ha sido procesado.");

        // Notificación urgente por SMS
        Notification urgentSMS = new UrgentNotification(new SMSSender());
        urgentSMS.notify("+34600000000", "Se ha detectado acceso no autorizado.");

        // Notificación urgente por Push
        Notification urgentPush = new UrgentNotification(new PushSender());
        urgentPush.notify("device-token-xyz", "Tu contraseña ha sido cambiada.");

        // Notificación normal por Push
        Notification normalPush = new NormalNotification(new PushSender());
        normalPush.notify("device-token-abc", "Tienes un nuevo mensaje.");
    }
}

/*
Salida esperada:
[EMAIL] Para: usuario@ejemplo.com | Mensaje: Tu pedido ha sido procesado.
[SMS] Para: +34600000000 | Mensaje: 🚨 URGENTE: Se ha detectado acceso no autorizado.
[PUSH] Para: device-token-xyz | Mensaje: 🚨 URGENTE: Tu contraseña ha sido cambiada.
[PUSH] Para: device-token-abc | Mensaje: Tienes un nuevo mensaje.
*/

Como puedes observar, añadir un nuevo canal de envío solo requiere crear una nueva clase que implemente MessageSender. Del mismo modo, añadir un nuevo tipo de notificación solo requiere extender Notification. Las dos jerarquías crecen de manera completamente independiente.

¿Cuándo usarlo?

  • Cuando quieres evitar una jerarquía de clases que crezca exponencialmente al combinar múltiples dimensiones de variación.
  • Cuando necesitas poder cambiar la implementación en tiempo de ejecución sin afectar al cliente.
  • Cuando tanto la abstracción como la implementación deben poder extenderse mediante herencia de forma independiente.
  • Cuando trabajas con plataformas o entornos múltiples (por ejemplo, diferentes bases de datos, sistemas operativos o protocolos de red) y necesitas aislar el código de negocio de los detalles de cada plataforma.
  • Cuando quieres compartir una implementación entre múltiples objetos de abstracción sin que el cliente sea consciente de ello.

Ventajas y desventajas

Ventajas

  • Principio Open/Closed: puedes añadir nuevas abstracciones e implementaciones sin modificar el código existente.
  • Principio de Responsabilidad Única: la abstracción se centra en la lógica de alto nivel y la implementación en los detalles concretos.
  • Reducción del acoplamiento: el cliente solo conoce la abstracción, no los detalles de la implementación.
  • Flexibilidad en tiempo de ejecución: la implementación puede cambiarse dinámicamente, lo que facilita la inyección de dependencias y las pruebas unitarias.
  • Escalabilidad: elimina la explosión de subclases al permitir que dos dimensiones de variación crezcan de forma lineal en lugar de multiplicativa.

Desventajas

  • Incremento de complejidad inicial: introducir dos jerarquías y una referencia entre ellas puede resultar excesivo para problemas simples donde solo existe una dimensión de variación.
  • Mayor número de clases: aunque evita la explosión de subclases, sigue añadiendo más artefactos al proyecto, lo que puede dificultar la navegación del código si no se documenta correctamente.
  • Indirección adicional: las llamadas pasan a través de la abstracción antes de llegar a la implementación, lo que introduce un nivel de indirección que puede resultar confuso para desarrolladores no familiarizados con el patrón.
