Decorator en Java: Agregando comportamiento sin modificar clases

Cómo extender responsabilidades dinámicamente mediante Decorator sin tocar el código base existente.

← Volver a la categoría

¿Qué es el patrón Decorator?

El patrón Decorator es un patrón de diseño estructural que permite agregar comportamiento adicional a un objeto de forma dinámica, en tiempo de ejecución, sin necesidad de modificar su clase original ni crear una jerarquía de subclases interminable. En lugar de heredar, el Decorator envuelve al objeto original y delega las llamadas a él, añadiendo lógica antes o después de cada operación.

Este patrón es especialmente valioso cuando necesitamos combinar varias responsabilidades de manera flexible. Imagina un sistema de notificaciones donde un mensaje puede enviarse por email, también loguearse, también cifrarse y también comprimirse: con Decorator, cada una de esas capacidades se convierte en una capa independiente que podemos apilar a voluntad.

En el ecosistema Java, el ejemplo más clásico lo encontramos en el paquete java.io: BufferedReader decora a FileReader, DataInputStream decora a FileInputStream, y así sucesivamente. Toda esa cadena de envolvimiento es Decorator en acción.

Problema que resuelve

Supongamos que tenemos un servicio de texto que formatea un mensaje. Con el tiempo, el negocio pide que algunos mensajes vayan en mayúsculas, otros con un prefijo especial, otros con ambas cosas, y quizá en el futuro con marcas de tiempo. Si resolvemos esto con herencia, la explosión de subclases es inevitable:

  • TextoEnMayusculas
  • TextoConPrefijo
  • TextoEnMayusculasConPrefijo
  • TextoConMarcaDeTiempo
  • TextoEnMayusculasConMarcaDeTiempo
  • … y así al infinito.

Cada combinación nueva implica una clase nueva. Esto viola el principio Open/Closed (abierto para extensión, cerrado para modificación) y hace que el código sea muy difícil de mantener. Además, si queremos cambiar el comportamiento de un objeto concreto en tiempo de ejecución según alguna condición, la herencia directamente no nos lo permite.

El patrón Decorator resuelve exactamente este problema: en lugar de crear subclases para cada combinación posible, creamos pequeñas clases decoradoras que se pueden encadenar libremente.

Estructura y conceptos principales

El patrón se compone de cuatro elementos fundamentales que trabajan en conjunto:

  • Componente (interfaz o clase abstracta): Define la operación o contrato que tanto el componente concreto como los decoradores deben respetar. Es el tipo común que permite intercambiarlos.
  • Componente Concreto: La implementación base del componente. Es el objeto "real" al que se le quiere agregar comportamiento. No conoce ni depende de ningún decorador.
  • Decorador Base: Clase abstracta (o concreta) que implementa el componente y mantiene una referencia al mismo mediante composición. Delega las llamadas al componente envuelto. Sirve como punto de extensión para todos los decoradores concretos.
  • Decoradores Concretos: Extienden al decorador base y añaden el comportamiento específico antes o después de delegar al componente. Cada decorador tiene una única responsabilidad.

La clave está en la composición: un decorador envuelve a otro decorador, que a su vez envuelve al componente concreto, formando una cadena. El cliente solo conoce la interfaz del componente y no necesita saber cuántas capas hay por debajo.

Ejemplo en Java

Veamos el patrón aplicado a un formateador de texto. Primero definimos la interfaz y el componente concreto: 


// Componente: interfaz común
public interface FormateadorTexto {
    String formatear(String texto);
}

// Componente Concreto: implementación base sin decoraciones
public class TextoSimple implements FormateadorTexto {

    @Override
    public String formatear(String texto) {
        return texto;
    }
}

// Decorador Base: mantiene referencia al componente y delega
public abstract class DecoradorTexto implements FormateadorTexto {

    private final FormateadorTexto envuelto;

    public DecoradorTexto(FormateadorTexto envuelto) {
        this.envuelto = envuelto;
    }

    @Override
    public String formatear(String texto) {
        return envuelto.formatear(texto);
    }
}

Ahora creamos dos decoradores concretos: uno que convierte el texto a mayúsculas y otro que agrega un prefijo personalizado: 


// Decorador Concreto 1: convierte el resultado a mayúsculas
public class DecoradorMayusculas extends DecoradorTexto {

    public DecoradorMayusculas(FormateadorTexto envuelto) {
        super(envuelto);
    }

    @Override
    public String formatear(String texto) {
        return super.formatear(texto).toUpperCase();
    }
}

// Decorador Concreto 2: agrega un prefijo al resultado
public class DecoradorPrefijo extends DecoradorTexto {

    private final String prefijo;

    public DecoradorPrefijo(FormateadorTexto envuelto, String prefijo) {
        super(envuelto);
        this.prefijo = prefijo;
    }

    @Override
    public String formatear(String texto) {
        return prefijo + super.formatear(texto);
    }
}

// Decorador Concreto 3: agrega una marca de tiempo al final
public class DecoradorMarcaTiempo extends DecoradorTexto {

    public DecoradorMarcaTiempo(FormateadorTexto envuelto) {
        super(envuelto);
    }

    @Override
    public String formatear(String texto) {
        long timestamp = System.currentTimeMillis();
        return super.formatear(texto) + " [" + timestamp + "]";
    }
}

Finalmente, combinamos los decoradores en tiempo de ejecución según las necesidades del cliente: 


public class Main {

    public static void main(String[] args) {

        // Solo el componente base
        FormateadorTexto simple = new TextoSimple();
        System.out.println(simple.formatear("hola mundo"));
        // Salida: hola mundo

        // Texto en mayúsculas
        FormateadorTexto mayusculas = new DecoradorMayusculas(new TextoSimple());
        System.out.println(mayusculas.formatear("hola mundo"));
        // Salida: HOLA MUNDO

        // Prefijo + mayúsculas: apilamos decoradores
        FormateadorTexto conPrefijo = new DecoradorPrefijo(
            new DecoradorMayusculas(new TextoSimple()),
            ">> "
        );
        System.out.println(conPrefijo.formatear("hola mundo"));
        // Salida: >> HOLA MUNDO

        // Prefijo + mayúsculas + marca de tiempo
        FormateadorTexto completo = new DecoradorMarcaTiempo(
            new DecoradorPrefijo(
                new DecoradorMayusculas(new TextoSimple()),
                ">> "
            )
        );
        System.out.println(completo.formatear("hola mundo"));
        // Salida: >> HOLA MUNDO [1718123456789]
    }
}

Observa cómo cada combinación se construye componiendo objetos, sin crear ninguna clase nueva. El orden de apilamiento importa: el decorador más externo es el último en ejecutarse sobre el resultado final.

¿Cuándo usarlo?

  • Cuando necesitas agregar responsabilidades a objetos individuales de manera dinámica y transparente, sin afectar a otros objetos de la misma clase.
  • Cuando la herencia no es viable porque el número de combinaciones posibles de comportamientos haría explotar la jerarquía de clases.
  • Cuando quieres seguir el principio Open/Closed: extender el comportamiento sin tocar el código existente, reduciendo el riesgo de introducir errores en funcionalidad ya probada.
  • Cuando trabajas con funcionalidades transversales como logging, caché, validación, compresión o cifrado, que pueden aplicarse de forma independiente sobre distintas implementaciones.
  • Cuando el comportamiento a añadir puede retirarse fácilmente: al ser composición, basta con no incluir ese decorador en la cadena.

Ventajas y desventajas

Ventajas

  • Flexibilidad en tiempo de ejecución: los comportamientos se pueden agregar y combinar dinámicamente sin recompilar ni modificar clases existentes.
  • Principio de responsabilidad única: cada decorador tiene una única función bien definida, lo que facilita el mantenimiento y las pruebas unitarias independientes.
  • Alternativa limpia a la herencia: evita jerarquías profundas y la duplicación de código que surge cuando se intenta modelar combinaciones mediante subclases.
  • Composición abierta: el cliente puede construir la cadena que necesita, incluso con decoradores definidos en módulos o librerías separadas.

Desventajas

  • Depuración más compleja: al haber varias capas de envolvimiento, rastrear un error en el stack trace puede ser más difícil, ya que el flujo de ejecución atraviesa múltiples clases antes de llegar al componente concreto.
  • Proliferación de objetos pequeños: si la cadena de decoradores crece mucho, se crean muchos objetos anidados que pueden afectar la legibilidad del código de construcción y, en casos extremos, la memoria.
  • El orden importa: el resultado puede variar según cómo se apilen los decoradores, lo que requiere un entendimiento claro del comportamiento de cada uno y puede generar errores sutiles si el orden no es el esperado.
  • No apto para modificar la interfaz: el Decorator solo puede extender el comportamiento de los métodos definidos en el componente. Si necesitas agregar métodos nuevos, este patrón no es la herramienta adecuada.
